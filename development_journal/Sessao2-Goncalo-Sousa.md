# Sessão 2 - 3 de junho de 2026

## Objetivo:
Migrar a aplicação Ancient Coins do armazenamento local com Ionic Storage para Supabase, seguindo a documentação fornecida pelo professor e mantendo a estrutura dos services simples, com operações CRUD diretas sobre a base de dados.

## Atividades realizadas:
- Configurei o projeto para utilizar Supabase como base de dados externa;
- Instalei a dependência `@supabase/supabase-js`;
- Criei o ficheiro `supabase.client.ts` para centralizar a criação do cliente Supabase;
- Adicionei as chaves e o URL do Supabase aos ficheiros de environment da aplicação;
- Removi a utilização do Ionic Storage e do `DatabaseService`, pois os dados passaram a ser obtidos diretamente da base de dados;
- Atualizei o `AppModule`, removendo a configuração relacionada com armazenamento local;
- Criei, com apoio de inteligência artificial, o ficheiro `supabase-setup.sql` com a estrutura das tabelas, dados iniciais, permissões e policies necessárias;
- Migrei os services da aplicação para passarem a trabalhar diretamente com o Supabase, mantendo cada um responsável pela sua área: utilizadores, moedas, mercado, conversas, mensagens e reviews;
- Atualizei o `AuthService` para usar Supabase Auth no registo, login, logout e recuperação da sessão atual;
- Removi a palavra-passe da tabela `users`, deixando essa responsabilidade para o Supabase Auth;
- Criei um trigger na base de dados para criar automaticamente o perfil em `public.users` quando um utilizador é criado em `auth.users`;
- Atualizei os modelos TypeScript para seguirem a mesma convenção de nomes da base de dados, usando campos como `owner_id`, `auth_id`, `created_at` e `total_reviews`;
- Separei os modelos TypeScript em ficheiros individuais, ficando cada model no seu próprio ficheiro;
- Simplifiquei o código dos services, removendo arrays locais e lógica que já não era necessária depois da migração para Supabase;
- Ajustei o registo para redirecionar o utilizador para a página de login após a criação da conta;

## Problemas:
- Foi necessário perceber a diferença entre os utilizadores da tabela `public.users` e os utilizadores geridos pelo Supabase Auth;
- A utilização da chave pública do Supabase no browser exigia Row Level Security e policies bem configuradas;
- O registo de novos utilizadores causava erro de RLS quando a aplicação tentava criar diretamente o perfil na tabela `users`;
- Com a confirmação de email ativa, o Supabase podia criar a conta sem devolver imediatamente uma sessão autenticada;
- A convenção de nomes entre TypeScript e base de dados estava inicialmente diferente, obrigando a conversões desnecessárias;

## Solução:
- Para separar os utilizadores da aplicação dos utilizadores de autenticação, mantive a tabela `public.users` para os dados de perfil e liguei-a ao Supabase Auth através do campo `auth_id`;
- Como a chave pública do Supabase é usada no browser, ativei Row Level Security e defini policies para controlar que dados cada utilizador autenticado pode consultar ou alterar;
- Para resolver o erro de RLS no registo, deixei de criar o perfil diretamente no frontend e adicionei um trigger que cria automaticamente a linha em `public.users` quando nasce um utilizador em `auth.users`;
- Para remover a lógica antiga do armazenamento local, eliminei o `DatabaseService` e passei os services a usar diretamente chamadas do Supabase, como `select`, `insert`, `update` e `delete`;
- Para evitar conversões desnecessárias entre o código e a base de dados, atualizei os modelos TypeScript para usarem a mesma convenção de nomes das tabelas;
- Para melhorar a organização do código, dividi o ficheiro geral de models em ficheiros específicos, como `user.model.ts`, `coin.model.ts`, `conversation.model.ts`, `message.model.ts` e `review.model.ts`;


## Decisões:
- Usar Supabase como backend principal da aplicação, substituindo o armazenamento local usado na fase anterior;
- Usar Supabase Auth para autenticação, em vez de guardar e validar passwords manualmente;
- Manter uma tabela `users` própria para guardar dados de perfil da aplicação, mas ligada ao Auth através de `auth_id`;
- Criar os perfis automaticamente através de trigger na base de dados, evitando inserts diretos no registo da aplicação;
- Usar a mesma convenção de nomes na base de dados e no TypeScript para evitar mapeamentos desnecessários;
- Separar os models por ficheiro para facilitar a leitura e a manutenção do projeto;
- Deixar a base de dados responsável pela criação dos ids, através de colunas `GENERATED BY DEFAULT AS IDENTITY`;
